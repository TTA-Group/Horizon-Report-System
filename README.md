# Horizon Report System

ระบบแจ้งเรื่องภายในสำนักงานผ่าน **LINE LIFF** — พนักงานแจ้งปัญหาภายในออฟฟิศผ่าน LINE Official Account
ระบบส่งเรื่องถึงฝ่ายที่รับผิดชอบ และให้ผู้แจ้งติดตามสถานะได้ตลอดเวลา

> ข้อกำหนดฉบับเต็ม: [`spec.md`](./spec.md) · ต้นแบบหน้าจอ: [`liff-report-mockup.html`](./liff-report-mockup.html)

---

## สแตกเทคโนโลยี

| ส่วน | เทคโนโลยี |
|---|---|
| Frontend (LIFF) | HTML/JS + `@line/liff` SDK (static) |
| Backend API | Cloudflare Workers (TypeScript) |
| ฐานข้อมูล | PostgreSQL (Supabase) |
| ไฟล์แนบ / สำรองข้อมูล | Supabase Storage |
| งานตามเวลา | Cloudflare Cron Triggers |

> เดิมใช้ Netlify ย้ายมา Cloudflare เพราะแผนฟรีของ Netlify จำกัดจำนวนครั้งที่ deploy ได้ต่อเดือน
> (`spec.md` หัวข้อ 2 และ 9 ยังอ้างถึง Netlify ตามข้อกำหนดฉบับแรก)

## โครงสร้างโปรเจกต์

```
public/          หน้าเว็บ LIFF — index.html, app.js, config.js (★ ตั้งค่า liffId ที่นี่)
src/index.ts     จุดเข้าของ Worker — จัดเส้นทาง /api/*, เสิร์ฟหน้าเว็บ, รันงานตามเวลา
src/api/         ตัวจัดการแต่ละ endpoint
  _lib/          โค้ดใช้ร่วม (db, auth, line, flex, jobs, reports, constants, env)
db/              schema.sql · seed.sql · enable-rls.sql · cleanup-sample-data.sql · reset-tickets.sql
                 add-followup.sql (เพิ่มคอลัมน์ของขั้นตอนแจ้งผลตรวจสอบ)
                 add-rating.sql (เพิ่มคอลัมน์ความพึงพอใจหลังปิดงาน)
                 import-employees.template.sql (นำเข้าพนักงานเป็นชุด — ห้ามใส่ข้อมูลจริงลงในที่เก็บโค้ด)
wrangler.toml    การตั้งค่า Worker (assets, nodejs_compat, cron triggers, LIFF_ID)
```

**API** (รายละเอียดใน `spec.md` หัวข้อ 6)
`/api/auth/*` ยืนยันตัวตนและผูกบัญชี · `/api/tickets*` แจ้งเรื่อง ติดตาม เปลี่ยนสถานะ ส่งต่อฝ่าย
แจ้งผลตรวจสอบ (`/assess`) อัปเดตความคืบหน้า (`/progress`) ·
`/api/admin/*` เพิ่มพนักงาน จัดการผู้ใช้งาน และกำหนดสถานะ (พนักงาน / ผู้รับผิดชอบฝ่าย / หัวหน้าฝ่าย) ·
`/api/reports/*` สรุปงานรายสัปดาห์/รายเดือน · `/api/uploads` ภาพแนบ · `/api/line/webhook` รับ postback จาก LINE

**คำสั่งในกลุ่มไลน์** — พิมพ์ `groupid` เพื่อขอรหัสกลุ่มสำหรับตั้งค่า `departments.line_group_id`
(ตอบกลับด้วย reply จึงไม่กินโควตา)

`GET /api/health` เปิดได้โดยไม่ต้องล็อกอิน ใช้ไล่ปัญหาเวลาระบบล่ม — บอกว่าค่าตั้งค่าแต่ละตัว
ตั้งไว้แล้วหรือยัง (true/false เท่านั้น ไม่แสดงค่า) และต่อฐานข้อมูล/LINE ได้หรือไม่ พร้อมเวลาที่ใช้

**งานตามเวลา** เตือนซ้ำ (ทุก 15 นาที) · db-keepalive (รายวัน) · backup (รายสัปดาห์) ·
cleanup-files (รายเดือน) · usage-report (ต้นเดือน)

## ติดตั้ง

```bash
npm install
```

**ฐานข้อมูล** — รันตามลำดับ
```bash
psql "$DATABASE_URL" -f db/schema.sql
psql "$DATABASE_URL" -f db/seed.sql
psql "$DATABASE_URL" -f db/enable-rls.sql
```

**ตัวแปรสภาพแวดล้อม** — ดูรายการทั้งหมดใน `.env.example`
ตั้งค่าที่ Cloudflare → Worker → Settings → Variables and Secrets

ยกเว้น `LIFF_ID` ที่เขียนไว้ใน `wrangler.toml` ตรง ๆ — ค่านี้อยู่ใน `public/config.js` ซึ่ง
เบราว์เซอร์ของทุกคนโหลดไปอยู่แล้ว จึงไม่ใช่ความลับ ฝั่ง Worker ต้องรู้ค่านี้เพราะต้องประกอบลิงก์
"เปิดในแอป" ใส่ปุ่มบนการ์ด ถ้าไม่ได้ตั้ง ปุ่มจะถอยไปใช้การถามตอบด้วยการ์ดชิปในกลุ่มแบบเดิมแทน

⚠️ ตั้งเป็นชนิด **Secret** ทุกตัว — ค่าชนิด Text จะถูกล้างทุกครั้งที่ deploy และถูกพิมพ์ลง build log

⚠️ `STORAGE_BUCKET_URL` ต้องเป็น bucket แบบ **public** (ภาพต้องแสดงในแอปได้)
ส่วน `BACKUP_BUCKET_URL` ต้องเป็น bucket แบบ **private คนละตัวกัน** เพราะไฟล์สำรองมีข้อมูลส่วนบุคคล

**LIFF** — ระบุ `liffId` ใน `public/config.js`

```bash
npm run typecheck   # ตรวจชนิดข้อมูล
npm run dev         # รันโลคัลด้วย wrangler
npm run deploy      # deploy ขึ้น Cloudflare
```

Cloudflare จะ build และ deploy อัตโนมัติเมื่อมีการ push เข้า `main`

## ค่าคงที่หลัก (`spec.md` หัวข้อ 4)

| หมวด | ฝ่ายปลายทาง | คำนำหน้าเลขที่เรื่อง |
|---|---|---|
| `IT` IT Support / Help Desk | IT / IT Helpdesk | `IT-` |
| `FAC` ระบบปรับอากาศ ประปา ไฟฟ้า | ADMIN | `ADM-` |
| `CLN` ห้องน้ำ แม่บ้าน และความสะอาด | ADMIN | `CLN-` |
| `GEN` เรื่องอื่น ๆ | OTHER | `GEN-` |

หมวด `CLN` ส่งเข้าฝ่าย ADMIN ต่างจาก `spec.md` หัวข้อ 4 ที่แยกเป็นฝ่าย CLN — เพราะหน้างานจริง
งานระบบปรับอากาศกับงานแม่บ้านเป็นทีมเดียวกัน จึงรวมเป็นคิวเดียว ฝ่าย CLN ถูกปิดใช้งานไว้
(`is_active = false`) แต่ยังคงแถวไว้เผื่ออนาคตแยกทีม — ฝ่ายที่ปิดใช้งานจะไม่ขึ้นเป็นชิป
ในหน้าคิวงาน เพราะไม่มีทางมีงานเข้ามาให้กดดู

**ฝ่าย HR ไม่รับเรื่องแจ้ง** (`receives_tickets = false`) มีไว้กำหนดว่าใครเป็นผู้ดูแลระบบ —
ใครอยู่ในฝ่าย HR จะเห็นและใช้หน้า "ผู้ดูแล" ได้ทันที ไม่ต้องไปแก้ค่าตั้งค่าที่ Cloudflare
ฝ่ายที่ `receives_tickets = false` จะไม่โผล่ในตัวเลือกส่งต่อฝ่ายและไม่มีคิวงานของตัวเอง
(`ADMIN_EMPLOYEE_CODES` ยังใช้ได้อยู่ เก็บไว้เป็นทางสำรองกันกรณีที่ยังไม่มีใครอยู่ในฝ่าย HR เลย)

สถานะ: `pending → in_progress → completed` (+ `cancelled` จาก `pending` และ `in_progress`)
`completed` คือจุดจบ — `closed` เลิกใช้แล้ว คงไว้ให้เรื่องเก่าที่เคยปิดยังแสดงผลได้

## การอยู่ร่วมกับระบบอื่นบน LINE OA เดียวกัน

หนึ่ง OA ตั้ง webhook ได้ที่เดียว ระบบนี้จึงทำหน้าที่เป็นตัวกลาง — รับ event จาก LINE แล้ว
ส่งต่อ event ต้นฉบับ (พร้อม signature เดิม) ไปยัง `MASSAGE_WEBHOOK_URL` ให้ระบบเดิมทำงานต่อได้ตามปกติ
พร้อมจำกัดเวลารอ เพื่อไม่ให้การตอบกลับ LINE ช้าตามระบบปลายทาง

ข้อยกเว้นเดียวที่ไม่ส่งต่อ: ชุด event ที่เป็นของระบบนี้ล้วน ๆ (การกดปุ่มในการ์ด และคำสั่ง
`groupid` กับข้อความยกเลิก) ระบบเดิมไม่ได้ใช้ข้อมูลนี้ แต่จะถูกปลุกให้ทำงานทุกครั้งที่เจ้าหน้าที่กดปุ่ม
ถ้ามี event อื่นปนมาแม้แต่รายการเดียว จะส่งต่อทั้งก้อนตามเดิม — ห้ามตัดแก้ body เพราะ signature
ผูกกับ body ต้นฉบับ แก้แล้วระบบปลายทางจะตรวจไม่ผ่าน

⚠️ ทั้งสองระบบใช้โควตาข้อความรายเดือนของ OA ร่วมกัน — ข้อความที่ระบบส่งออกเอง (push) นับโควตา
ส่วนการตอบกลับทันทีหลังผู้ใช้ทัก (reply) ไม่นับ

## การแจ้งเตือนในกลุ่มไลน์

ทุกฝ่ายใช้**กลุ่มไลน์กลุ่มเดียวกัน** — ตั้ง `departments.line_group_id` เป็น groupId เดียวกันทุกแถว
เมื่อการ์ดของทุกทีมมาปนกันในที่เดียว ระบบจึงแยกให้ด้วยหน้าตาของการ์ด:

- **หัวการ์ดเป็นชื่อฝ่าย บนพื้นเขียว** — เขียวเดียวกับปุ่มท้ายการ์ด (สีเขียวของ LINE) เหมือนกันทุกฝ่าย
  ชื่อฝ่ายอ่านได้จากตัวหนังสืออยู่แล้ว สีจึงไม่ต้องทำหน้าที่นี้ซ้ำ
- **แถบความเร่งด่วนเต็มความกว้าง ใต้หัวการ์ด** — สีทึบ ปกติเทา · เร่งด่วนส้มเข้ม · เร่งด่วนมากแดง
  ทั้งสองแถบเป็นกล่องลูกใน `header` ที่ตัด padding ออก จึงกินเต็มความกว้างทั้งคู่ (ไม่ใช้ `hero`
  เพราะ box ใน hero ไม่ได้รองรับทุกเวอร์ชัน)
- **แถบขั้นตอนแนวนอน** — จุด·เส้น·จุด บอกว่าเรื่องเดินไปถึงขั้นไหนจาก แจ้งเรื่อง → รับเรื่อง →
  ตรวจสอบ → เสร็จสิ้น ขั้นที่ผ่านแล้วเป็นจุดทึบสีเขียวเข้ม ที่ยังไม่ถึงเป็นจุดกลวงสีจาง
  เรื่องที่ถูกยกเลิกจะตัดขั้นที่ไม่มีวันเกิดขึ้นทิ้ง แล้วจบด้วยจุดแดง "ยกเลิก"
- **กล่อง "ล่าสุด"** — คำนำหน้า / ชื่อคน / วันเวลา อย่างละบรรทัด ไม่แสดงตอนเรื่องเพิ่งแจ้งเข้ามา
  เพราะยังไม่มีใครทำอะไร และจะซ้ำกับชิปวันเวลาด้านบนกับแถวผู้แจ้งอยู่แล้ว
- **วันเวลาที่แจ้งเป็นชิปมุมขวาบน** อยู่แถวเดียวกับเลขที่เรื่อง ไม่กินบรรทัดในรายการข้อมูล
- **รูปภาพแนบกดดูได้จากในกลุ่ม** — รูปย่อไม่เกิน 3 รูปต่อหนึ่งแถว แตะแล้วเปิดขนาดเต็ม
  ในเบราว์เซอร์ของ LINE ไม่ต้องเปิดแอป (LINE ไปดึงรูปเอง ไฟล์จึงต้องอยู่ใน bucket สาธารณะ
  ตาม `STORAGE_BUCKET_URL`) รูปที่เกิน 3 บอกจำนวนไว้ให้ไปดูต่อในแอป
- **กล่อง "ยังไม่มีผู้รับผิดชอบ" กรอบแดง** — ขึ้นเฉพาะตอนที่ยังไม่มีใครกดรับเรื่องเท่านั้น
  พอมีคนรับแล้วกล่องนี้หายไป เพราะกล่อง "ล่าสุด" บอกชื่อคนนั้นไปแล้ว ไม่ต้องเขียนซ้ำสองที่

### การ์ดมีสองขนาด

รายละเอียดข้างต้นเป็น **ใบเต็ม** ซึ่งใช้เฉพาะตอนที่เรื่องยังไม่มีผู้รับ (`pending`) เท่านั้น
เพราะเป็นใบเดียวที่คนทั้งกลุ่มต้องอ่านให้ครบก่อนแย่งกันกดรับ พอมีเจ้าของแล้วทุกคนอ่านใบแรกไปแล้ว
การส่งข้อมูลชุดเดิมซ้ำอีก 5-6 รอบต่อหนึ่งเรื่องคือต้นเหตุที่กลุ่มล้น สถานะหลังจากนั้นจึงใช้ **ใบย่อ**
(`buildCompactFlex`) ซึ่งสูงราวครึ่งเดียว อ่านออกตั้งแต่ยังไม่ทันอ่านตัวหนังสือว่านี่คือใบตามงาน
ไม่ใช่งานใหม่ที่ต้องรีบกดรับ

ทั้งสองใบใช้ฟองขนาดเดียวกัน (`kilo`) — การ์ดของเรื่องเดียวกันที่กว้างไม่เท่ากันทำให้บทสนทนา
ในกลุ่มดูขรุขระ ความต่างระหว่างสองใบควรมาจากปริมาณข้อมูล ไม่ใช่ความกว้างของฟอง

ขนาดตัวหนังสือทุกใบอ่านจากตาราง `FS` ที่เดียวใน `flex.ts` เป็นค่าพิกเซล ไม่ใช่คำสำเร็จรูปของ
Flex (`xxs`=11 `xs`=13 `sm`=14 `md`=16 `lg`=19) ซึ่งกระโดดทีละ 2-3px และเล็กสุดหยุดแค่ 11 —
ชุดนี้เล็กกว่าค่ามาตรฐานราว 1-2px ทั้งใบ (17 / 15 / 14 / 13 / 12 / 10) เพราะการ์ดมีข้อมูล
หลายชั้นในพื้นที่แคบ ตัวหนังสือที่เล็กลงคือที่ว่างที่เพิ่มขึ้นโดยไม่ต้องตัดข้อมูลอะไรออก

| | ใบเต็ม (`pending`) | ใบย่อ (สถานะอื่น) |
|---|---|---|
| ความกว้าง | `kilo` | `kilo` (เท่ากัน) |
| หัวการ์ด | ชื่อฝ่ายบนพื้นเขียว + แถบความเร่งด่วนอีกแถบ | แถบเดียว ชื่อฝ่ายซ้าย ความเร่งด่วนขวา บนพื้นสีความเร่งด่วน |
| เรื่องที่แจ้ง | แถวข้อมูล "รายละเอียด" เต็ม | หัวเรื่องตัวหนา จำกัด 2 บรรทัด |
| ผู้แจ้ง · ต้นสังกัด · หมวดหมู่ · เวลาที่แจ้ง | มี | ตัดออก |
| รูปภาพแนบ | มี | ตัดออก (ดูต่อในแอปหรือบนใบแรกที่ยังอยู่ในกลุ่ม) |
| แถบขั้นตอน · กล่อง "ล่าสุด" | มี | มี |
| อาการที่พบ · กำหนดเสร็จ | — | ขึ้นเองเมื่อแจ้งผลแล้ว |

### ขั้นตอนหลังรับเรื่อง

กดรับเรื่องแล้วไม่ใช่จบ — ผู้รับผิดชอบต้องแจ้งกลับว่า **พบอะไร** และ **จะเสร็จเมื่อไหร่**
ก่อนที่เรื่องจะนับว่าผ่านขั้น "ตรวจสอบ"

1. กด **แจ้งผลตรวจสอบ** บนใบย่อ → เปิดแอปเต็มจอทับหน้าแชท ไปที่เรื่องนั้นและหน้ากรอกทันที
2. เลือกกรอบเวลาจากชิป 9 ตัวเลือก → ได้ `due_at` เป็นเวลาจริง (ตัวเลือกที่นับเป็นวันไปจบที่
   18:00 น. ของวันนั้น) ส่วน "เลือกวันเอง" กับ "รออะไหล่" เผยช่องปฏิทินให้เลือกวัน
3. พิมพ์อาการที่พบ หรือติ๊ก **ไม่มีคำอธิบายเพิ่มเติม** — อย่างใดอย่างหนึ่งเสมอ เว้นว่างทั้งคู่ไม่ได้
4. ครบทั้งสองอย่างจึงตั้ง `assessed_at` แล้วส่งข้อความเดียวถึงผู้แจ้ง บอกอาการ กำหนดเสร็จ และผู้รับผิดชอบ
   พร้อมส่งใบย่อใบใหม่เข้ากลุ่ม

**กำหนดเสร็จต้องเป็นปุ่มให้กด ไม่ใช่ช่องให้พิมพ์** — ข้อความอย่าง "ประมาณอาทิตย์หน้า"
ระบบไม่รู้ว่าคือวันไหน จึงทวงต่อไม่ได้ พอเป็นค่าที่เทียบเวลาได้ ระบบถึงจะไล่ตามเองได้จริง
รายการตัวเลือกอยู่ที่ `DUE_OPTIONS` ที่เดียว แล้วส่งให้หน้าจอผ่าน `/api/masters`
จะได้ไม่มีรายการซ้ำสองที่ให้เผลอแก้ไม่ตรงกัน

### ทำไมย้ายมาทำในแอป

ขั้นตอนนี้เคยถามตอบด้วยการ์ดชิปในกลุ่ม ซึ่งกินพื้นที่ 2-3 ใบต่อหนึ่งเรื่องทั้งที่เป็นบทสนทนา
ระหว่างระบบกับผู้รับผิดชอบคนเดียว คนอื่นในกลุ่มไม่ได้ใช้อะไรจากใบพวกนั้นเลย

ปุ่มบนใบย่อจึงเป็นลิงก์ `https://liff.line.me/<LIFF_ID>?ticket=<id>&do=assess` แตะแล้วเปิดแอป
ตรงเข้าเรื่องนั้น ปิดแล้วกลับมาที่กลุ่มเหมือนเดิม การเปิดแอปไม่กินโควตาข้อความ และหน้าจอกว้างพอ
จะเห็นตัวเลือกทั้งหมดพร้อมกัน แนบรูปหลังซ่อมได้ ซึ่งการ์ดในกลุ่มทำไม่ได้

ปุ่มในกลุ่มซ่อนรายคนไม่ได้ ทุกคนที่เห็นการ์ดจึงกดได้ — คนที่ไม่ใช่เจ้าหน้าที่ของฝ่ายจะได้
**หน้ารายละเอียดแบบดูอย่างเดียว** ไม่ใช่ข้อความว่าไม่มีสิทธิ์ เพราะการเปิดดูสถานะเรื่องไม่ใช่
เรื่องต้องห้าม ด่านที่ตัดสินว่าใครทำอะไรได้จริงคือ `can_act` จาก `/api/tickets/:id`

**ปิดงานได้จากในกลุ่มแตะเดียว เมื่อแจ้งผลไปแล้ว** — ตอนนั้นข้อมูลที่ต้องบันทึกครบแล้ว เหลือแค่
บอกว่าเสร็จ ซึ่งช่างที่ยืนอยู่หน้างานควรกดได้โดยไม่ต้องเปิดแอป (postback = การตอบกลับ ไม่กินโควตา)
แต่ถ้า **ยังไม่เคยแจ้งผลเลย** ปุ่มปิดงานจะพาไปกรอกในแอปก่อน แล้วบันทึกกับปิดงานให้ในคราวเดียว
(`then_complete`) — เรื่องที่เปิดแล้วปิดโดยไม่มีใครรู้ว่าเกิดอะไรขึ้นคือช่องโหว่ที่ตั้งใจอุด

### หน้าคิวงาน

คิวงานแบ่งเป็น 4 หน้าด้วยชิปด้านบน แต่ละหน้าเป็นคำถามคนละคำถาม:

| หน้า | เห็นอะไร | เรียงตาม |
|---|---|---|
| ทั้งหมด | ทุกเรื่องของฝ่าย รวมที่จบแล้ว | ความเร่งด่วน แล้วใหม่สุดก่อน |
| รอรับเรื่อง | เรื่องที่ยังไม่มีใครกดรับ | ความเร่งด่วน แล้วใหม่สุดก่อน |
| งานที่รับผิดชอบ | งานของตัวเองที่ยังไม่จบ (`pending` / `in_progress`) | ความเร่งด่วน แล้วใหม่สุดก่อน |
| งานที่จบแล้ว | งานของตัวเองที่จบหรือถูกยกเลิก | จบล่าสุดขึ้นก่อน |

งานที่จบไปแล้วเป็นประวัติ ไม่ใช่สิ่งที่ต้องเห็นตอนไล่ดูว่าเหลืออะไรต้องทำ ปนกันแล้วรายการ
ยาวขึ้นเรื่อย ๆ จนหาของจริงไม่เจอ ฝั่ง API แยกด้วยพารามิเตอร์ `group=active|done`
และการ์ดของงานที่จบแล้วขึ้น "จบเมื่อ" / "ยกเลิกเมื่อ" แทน "คาดว่าเสร็จ" พร้อมตัดปุ่มดำเนินการทิ้ง

### ปิดงานแล้วถามความพึงพอใจ

ปิดงานแล้วผู้แจ้งได้ **การ์ดให้ดาว** แทนข้อความ "สถานะ: ดำเนินการเสร็จสิ้น" แบบเดิม —
ข้อความนั้นบอกสิ่งที่ผู้แจ้งรู้อยู่แล้ว (ของที่เสียกลับมาใช้ได้แล้ว) และไม่ได้เปิดโอกาสให้ทำอะไรต่อ

1. แตะดาว 1–5 ดวง → บันทึกคะแนนทันทีตั้งแต่ขั้นนี้ ไม่รอให้ตอบครบสองขั้น เพราะคนส่วนใหญ่
   กดดาวแล้วหยุด ถ้ารอจนจบคะแนนส่วนใหญ่จะหายไป
2. ระบบตอบชิปให้เลือกต่อ — **4-5 ดาวได้ชิปคำชม** (เสร็จไวมาก · แก้ปัญหาได้ดี · ใส่ใจดูแลดี ·
   อธิบายชัดเจน · สุภาพเป็นกันเอง) ส่วน **1-3 ดาวได้ชิปสิ่งที่ควรปรับปรุง** ทั้งสองแบบมีปุ่ม "ไม่เพิ่มเติม"
3. เลือกคำชมแล้ว ระบบส่ง **การ์ดคำชมถึงผู้รับผิดชอบ** พร้อมดาวและคำที่ผู้แจ้งเลือก

**คำติไม่ถูกส่งต่อ** — เก็บไว้ในระบบให้ดูย้อนหลังได้เท่านั้น ข้อความตำหนิที่เด้งเข้าแชทส่วนตัว
โดยที่เจ้าตัวไม่ได้ขอ ไม่ได้ทำให้งานครั้งหน้าดีขึ้น

ทั้งหมดเป็นตัวเลือกให้กด ไม่มีช่องให้พิมพ์ เพราะคนที่ต้องกดคือผู้แจ้งที่งานของตัวเองจบไปแล้ว
ถ้าต้องพิมพ์จะไม่มีใครตอบ · ข้อมูลที่ฝากไปกับปุ่มเป็นลำดับของชิป ไม่ใช่ตัวหนังสือ เพราะไลน์จำกัด
ความยาวไว้ 300 ตัวอักษร และภาษาไทยหนึ่งตัวกินไป 9 ตัวเมื่อเข้ารหัสใส่ URL

**เรื่องโควตา** ใบถามความพึงพอใจใช้ที่ของข้อความ "เสร็จสิ้น" เดิม จึงเท่าทุน ขั้นที่เหลือเป็นการ
ตอบกลับซึ่งไม่กินโควตา มีเพียงการ์ดคำชมถึงผู้รับผิดชอบที่เพิ่มมา 1 ข้อความ และเกิดเฉพาะตอนที่
ผู้แจ้งเลือกคำชมจริง ๆ

กรณีที่ผู้แจ้งกับผู้รับผิดชอบเป็นคนเดียวกัน (เจ้าหน้าที่แจ้งเรื่องของตัวเองแล้วซ่อมเอง) ระบบข้ามทั้งหมด

### การทวงหลังรับเรื่อง

งานเตือนซ้ำเดิมมองเฉพาะเรื่องที่ยังไม่มีผู้รับ พอมีคนกดรับ เรื่องนั้นหลุดจากการเตือนถาวร
`runProgressReminders()` อุดรูนั้น — ส่งถึงผู้รับผิดชอบโดยตรง ไม่ลงกลุ่ม เพราะเป็นการทวงรายบุคคล

| กรณี | จังหวะ | ตอบได้จาก |
|---|---|---|
| รับเรื่องแล้วยังไม่แจ้งผลตรวจสอบ | ทุก 2 ชั่วโมง | ปุ่มบนใบย่อ (เปิดแอป) |
| เลยกำหนดที่แจ้งไว้ | ทุกวัน | ชิป เสร็จสิ้น / เลื่อนกำหนด |
| รออะไหล่ | ทุก 7 วัน ไม่จำกัดจำนวนครั้ง | ชิป ของมาแล้ว / เลื่อนวัน |

แจ้งหัวหน้าฝ่ายเพิ่มเมื่อเลยกำหนดมา 2 วัน หรือเลื่อนกำหนดมาแล้ว 3 ครั้ง —
กันไม่ให้ "รออะไหล่" กลายเป็นที่ซุกงานค้าง

### การ์ดเปลี่ยนตามสถานะ

LINE แก้ข้อความที่ส่งไปแล้วไม่ได้ ทุกครั้งที่สถานะเปลี่ยนระบบจึงตอบการ์ดใบใหม่ลงในกลุ่ม
การ์ดล่าสุดในบทสนทนาคือสถานะจริงเสมอ ส่วนการ์ดเก่าที่ค้างอยู่ยัง**กดได้ตามปกติ** — ถ้าสถานะ
เลยไปแล้ว ระบบจะตอบเหตุผลสั้น ๆ พร้อม**การ์ดล่าสุด**กลับมาในข้อความเดียว กดต่อจากใบใหม่ได้ทันที
ไม่ต้องเลื่อนหาการ์ดล่าสุดเอง

| สถานะ | ขนาด | แถบขั้นตอน | ปุ่ม |
|---|---|---|---|
| `pending` | ใบเต็ม | ●—○—○—○ | รับเรื่อง · ยกเลิกเรื่อง |
| `in_progress` ยังไม่แจ้งผล | ใบย่อ | ●—●—○—○ | **แจ้งผลตรวจสอบ** (เปิดแอป) · ดำเนินการเสร็จสิ้น (เปิดแอป) |
| `in_progress` แจ้งผลแล้ว | ใบย่อ | ●—●—●—○ | ดำเนินการเสร็จสิ้น (กดจบในกลุ่ม) · อัปเดตความคืบหน้า (เปิดแอป) |
| `completed` | ใบย่อ | ●—●—●—● | ไม่มี — เหลือไว้เป็นบันทึก |
| `cancelled` | ใบย่อ | ●—[●]—● จุดสุดท้ายแดง | ไม่มี |

ปุ่ม **ยกเลิกเรื่อง** อยู่บนใบเต็มเท่านั้น เรื่องที่มีเจ้าของแล้วยกเลิกได้จากหน้าคิวงานในแอป
หรือพิมพ์ `ยกเลิก <เลขที่เรื่อง>: <เหตุผล>` ในกลุ่มตามเดิม

เรื่องที่จบไปแล้วถือว่าผ่านขั้น "ตรวจสอบ" มาแล้วเสมอ เรื่องเก่าก่อนมีขั้นนี้จึงไม่ค้างเป็นจุดกลวง

ความเคลื่อนไหวล่าสุดอ่านมาจาก `ticket_events` ด้วย LATERAL join ในคำสั่งเดียวกับที่อ่านตัวเรื่อง
จึงไม่ได้เพิ่มรอบวิ่งไปฐานข้อมูล และกรอง `actor_id IS NULL` ทิ้ง เพื่อไม่ให้รายการ "เตือนซ้ำ"
ของระบบไปแทนที่ชื่อคนที่ทำงานจริง

**ทุกการ์ดบอกชื่อคนที่ทำ** — กล่อง "ล่าสุด" บอกคนที่เพิ่งทำรายการ พร้อมคำนำหน้าตามสถานะ
(`รับเรื่องและรับผิดชอบโดย` / `ดำเนินการเสร็จสิ้นโดย` / `ยกเลิกโดย` / `ส่งต่อมาโดย`)
ชื่อผู้รับผิดชอบจะขึ้นเป็นแถวข้อมูลเพิ่มเฉพาะตอนที่ไม่ใช่คนเดียวกับคนที่ทำรายการล่าสุด
เช่น A รับเรื่องไว้แต่ B เป็นคนกดปิดงาน — ถ้าเป็นคนเดียวกันไม่ต้องเขียนซ้ำ

การเปลี่ยนสถานะจากหน้าแอปก็ส่งการ์ดเข้ากลุ่มเหมือนกัน กลุ่มจึงไม่ค้างอยู่ที่การ์ดเก่า
ไม่ว่าคนทำงานจะกดจากในกลุ่มหรือในแอป

**การยกเลิกต้องมีเหตุผลเสมอ** — ปุ่ม "ยกเลิกเรื่อง" ใช้ `inputOption: openKeyboard` เปิดแป้นพิมพ์
พร้อมข้อความตั้งต้น `ยกเลิก <เลขที่เรื่อง>: ` ให้พิมพ์เหตุผลต่อท้ายแล้วส่ง ตัวเลขที่เรื่องอยู่ในข้อความ
อยู่แล้ว ระบบจึงไม่ต้องเก็บสถานะค้างว่าใครกำลังยกเลิกเรื่องไหน เหตุผลถูกบันทึกลง `ticket_events`
และส่งให้ผู้แจ้งทราบ

การกดปุ่มไม่โพสต์ข้อความลงกลุ่ม (ไม่ใส่ `displayText`) — การ์ดใบใหม่บอกครบอยู่แล้วว่าใครรับเรื่อง
และสถานะเปลี่ยนเป็นอะไร

### การเตือนถึงตัวคน

**บัญชีทางการของ LINE ส่ง @mention ไม่ได้** — ทดลองแล้วทั้งเรียกรายคน (`type: "user"` พร้อม
userId ที่ตรวจแล้วว่าตรง) และเรียกทั้งกลุ่ม (`type: "all"` ซึ่งไม่ใช้ userId เลย) LINE ตอบ 200
ทั้งสองแบบแล้วทิ้งส่วนที่เป็นการเรียกทิ้งเงียบ ๆ ข้อความออกมาเป็นตัวหนังสือธรรมดา ไม่มี error ให้ไล่
การ์ดในกลุ่มจึงปลุกคนที่ปิดเสียงกลุ่มไว้ไม่ได้

ระบบจึงใช้ **ข้อความส่วนตัว เฉพาะตอนงานค้างเกินกำหนด** แทน — แจ้งเข้ากลุ่มก่อนตามปกติ
ถ้าเกิน `departments.sla_ack_minutes` (ตั้งไว้ 15 นาที) แล้วยังไม่มีใครกดรับเรื่อง งานเตือนซ้ำ
จะส่งข้อความส่วนตัวหาเจ้าหน้าที่ของฝ่ายนั้นทุกคน **รอบเดียว** จากนั้นรอบถัดไปเตือนในกลุ่ม
และส่งถึงหัวหน้าฝ่าย (`escalate_to`) แทน

เหตุผลที่ไม่ส่งส่วนตัวทุกเรื่องตั้งแต่แรก: แต่ละข้อความนับโควตารายเดือนของ OA ที่ใช้ร่วมกับระบบอื่น
เรื่องที่มีคนรับภายใน 15 นาทีจึงไม่ต้องรบกวนใครเพิ่มเลย

**ความเร็วตอนกดปุ่ม** — คนกดปุ่มยืนรออยู่ ถ้าการ์ดเด้งช้าเขาจะกดซ้ำ ทาง webhook จึงอ่านทุกอย่าง
ที่ต้องใช้ (ผู้กด เรื่อง ฝ่าย สิทธิ์ ไลน์ของผู้แจ้ง) ด้วย query เดียว เปลี่ยนสถานะกับบันทึกประวัติด้วย
คำสั่งเดียวผ่าน CTE แล้ว **ตอบการ์ดก่อน** ค่อยแจ้งผู้แจ้งทีหลัง และถ้ากดซ้ำบนเรื่องที่ตัวเองรับไปแล้ว
ระบบจะตอบการ์ดปัจจุบันกลับไปเฉย ๆ แทนที่จะขึ้นข้อความว่าทำรายการไม่ได้

หัวหน้าฝ่ายและผู้ดูแลระบบ (HR) เปิดแท็บ **สรุปงาน** ในแอปเพื่อดูภาพรวมของฝ่ายได้ทุกเมื่อ
เลือกได้ 4 ช่วง: สัปดาห์นี้ · สัปดาห์ที่แล้ว · เดือนนี้ · เดือนที่แล้ว
(ค่าเริ่มต้นคือช่วงที่จบแล้ว เพราะเป็นตัวเลขที่เอาไปอ้างอิงได้จริง ไม่ใช่ตัวเลขที่ยังวิ่งอยู่)

หน้าจอมีตัวเลขสี่ตัวเท่านั้น — **แจ้งเข้ามา · ปิดจบไปแล้ว · ยังค้างอยู่ · เลยกำหนด**
ตั้งใจไม่ใส่กราฟและไม่ใส่ตัวชี้วัดประสิทธิภาพ เพราะคนที่เปิดดูต้องการรู้ว่าตอนนี้เหลืออะไร
ไม่ได้ต้องการแผงข้อมูลที่ต้องนั่งตีความ ของที่ใส่เพิ่มเข้ามาทุกชิ้นคือของที่ทำให้หน้าอ่านยากขึ้น

ตัวเลขแยก "ในช่วงนี้" (แจ้งเข้ามา/ปิดจบ) ออกจาก "ณ ปัจจุบัน" (ค้าง/เลยกำหนด) ในการคำนวณ
เพราะเป็นคนละคำถาม — งานค้างเป็นภาพนิ่งที่รวมของเก่าซึ่งค้างข้ามช่วงมาด้วย

### ไฟล์ที่เอาไปใช้อ้างอิง

ปุ่ม **เปิดรายงานฉบับเต็ม** เปิดหน้าเว็บที่มีตัวเลขสี่ตัวเดียวกัน แล้วต่อด้วย**ตารางรายการงาน
ทั้งหมดตารางเดียว** — เรื่องที่ยังค้าง ที่ปิดจบ และที่ยกเลิก อยู่รวมกันโดยมีป้ายสถานะบนแถวเป็นตัวแยก
เรียงจากเรื่องที่ต้องรีบที่สุด (เลยกำหนด → เร่งด่วน → เรื่องเก่าก่อน) ลงไปหาเรื่องที่จบแล้ว
มีช่องค้นหาสำหรับหาเรื่องเดียวในตารางยาว ๆ

จากหน้านั้นกด **พิมพ์ / บันทึก PDF** (จัดหน้า A4 แนวนอนไว้แล้ว) หรือ **ส่งออก CSV**
(มี BOM นำหน้า Excel บนวินโดวส์จึงเปิดภาษาไทยได้ไม่เพี้ยน)

ทำเป็นหน้าเว็บไม่ใช่ PDF เพราะ Worker สร้าง PDF ไม่ได้ถ้าไม่ลงไลบรารีหนัก ๆ และหน้าเว็บได้ประโยชน์
มากกว่า — ส่งลิงก์ให้เปิดจากมือถือได้ทันที หรือกดพิมพ์เป็น PDF แนบอีเมลก็ได้ จากไฟล์เดียว

**ลิงก์เปิดได้โดยไม่ต้องล็อกอิน** เพื่อให้ส่งต่อได้จริง สิ่งที่กันไว้แทนการล็อกอินคือ ลิงก์ถูกเซ็นกำกับ
ด้วยกุญแจของระบบ (แก้ฝ่ายหรือช่วงเวลาในลิงก์ไม่ได้ ลายเซ็นจะไม่ตรงทันที) และ **หมดอายุใน 14 วัน**
กุญแจแยกออกจาก `LINE_CHANNEL_SECRET` ด้วยการแฮชกับป้ายชื่อประจำงานนี้ จึงใช้แทนลายเซ็นของ
webhook ไม่ได้ และไม่ต้องเพิ่มค่าตั้งค่าใหม่

ระบบ**ไม่ส่งรายงานให้ใครเอง** — เป็นของที่เปิดดูเมื่อต้องการใช้ ไม่ใช่ข้อความที่เด้งเข้ามาทุกสัปดาห์

## สถานะการใช้งาน

**ใช้งานได้แล้ว** — ยืนยันตัวตนด้วยรหัสพนักงาน · แจ้งเรื่องพร้อมแนบภาพ (บีบอัดในเบราว์เซอร์) ·
ติดตามสถานะและยกเลิกเรื่องที่ยังไม่มีคนรับ · คิวงานของฝ่ายสำหรับเจ้าหน้าที่ (รับเรื่อง/แจ้งผลตรวจสอบ/เสร็จ/ส่งต่อ/ยกเลิก) ·
หน้าผู้ดูแลสำหรับ HR (เพิ่มพนักงานเข้าระบบ ค้นหา ระงับ–คืนสิทธิ์ ปลดการผูกบัญชีไลน์
กำหนดสถานะพนักงาน/ผู้รับผิดชอบฝ่าย/หัวหน้าฝ่าย) · รายงานสรุปงานรายสัปดาห์/รายเดือน พร้อมไฟล์ PDF/CSV สำหรับใช้อ้างอิง

การแต่งตั้งหัวหน้าฝ่ายจะตั้ง `departments.escalate_to` ให้เองโดยอัตโนมัติ (คำนวณใหม่จากหัวหน้า
ที่ยังทำงานอยู่ทุกครั้งที่มีการเปลี่ยนแปลง) จึงไม่มีทางเหลือปลายทางการเตือนซ้ำที่ชี้ไปหาคนที่ลาออกแล้ว

**ผูกบัญชีได้เฉพาะรหัสที่อยู่ในระบบแล้ว** — ต่างจาก `spec.md` หัวข้อ 5.1 ที่ให้คนซึ่งไม่พบรหัส
กรอกข้อมูลเองแล้วเข้าใช้งานได้ทันที (`source='self'`) ทางลัดนั้นถูกปิดแล้ว เพราะเท่ากับใครก็ตาม
ที่มีบัญชีไลน์สมัครเข้ามาเองได้ ตอนนี้ทะเบียนพนักงานอยู่ในระบบครบ และ HR เพิ่มคนใหม่เองได้
จากหน้าผู้ดูแล คนที่ไม่พบรหัสจะเห็นข้อความให้ติดต่อ HR แทน

**ยังต้องทำก่อนเปิดใช้ทั้งองค์กร**
- ตั้ง webhook ของ LINE มาที่ `/api/line/webhook` เพื่อให้ปุ่มในข้อความทำงาน
- ผูก `departments.line_group_id` ของทุกฝ่ายเป็นกลุ่มเดียวกัน (รับ `groupId` จาก event `join` ตอนเชิญ OA เข้ากลุ่ม)
- ทดสอบตามเกณฑ์ใน `spec.md` หัวข้อ 12 กับผู้ใช้จริงหนึ่งฝ่ายก่อน
